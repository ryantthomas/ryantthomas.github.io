dbt-llm-analytics

A free, hands-on course that teaches dbt on real National Park Service biodiversity data — 5,824 species and roughly 23,000 observations across four parks — and then adds a read-only MCP server so you can ask the finished warehouse questions in plain English.

dbt · DuckDB · Python · MCP · Killercoda

The problem

Most dbt tutorials run on jaffle_shop: a handful of tidy rows invented to make the example work. You finish having typed the commands without meeting the thing dbt actually exists for — real data with inconsistent categories, missing values, and columns whose meaning you have to go and check. The tests pass on the first try, so you never learn why tests are there.

The second gap is the ending. Tutorials stop at a built model, which is where the interesting question starts: now that the warehouse is modeled, who queries it, and how?

Architecture

The data ships as seed CSVs, so there's no warehouse to provision and no credentials to manage — DuckDB runs in-process. Four staging models clean and type the raw species and observation tables; three marts answer actual questions about conservation status and park diversity. Schema tests and column documentation live alongside the models in YAML, which is the part the tutorial spends the most time on.

On top sits llm_query/mcp_server.py: three tools — list_tables, describe_table, run_query — over the built DuckDB file, with run_query restricted to SELECT.

Three decisions worth explaining

Real public data instead of a synthetic example

Synthetic data makes a tutorial easier to write and worse to learn from, because every edge case has been removed in advance. The NPS dataset has inconsistent conservation-status values and sparse columns, so the staging layer has real work to do and a schema test can genuinely fail. The cost is a 1.5MB repo and a longer part two; the benefit is that the reader meets the problem dbt solves.

DuckDB rather than Postgres or a cloud warehouse

A cloud warehouse is more realistic and adds a signup, credentials, and a free-tier clock to step zero — which is where tutorials lose people. DuckDB runs in-process from a file, so dbt build works offline in seconds. What's lost is exposure to warehouse-specific SQL and permissions, which is the right thing to defer past someone's first dbt project.

SELECT-only, with the constraint in the server rather than the prompt

The MCP server hands a language model a SQL execution tool, so the question is what happens when it writes a DROP. Telling it not to in the tool description is not a control. The restriction is enforced in run_query before execution — the same principle as the prerequisite gate in learning-mcp: if a behavior matters, it belongs in the server, not the instructions.

Verification

The dbt project's own schema tests are the verification, which is the point of the exercise — not_null, unique, and accepted-values tests over the staging and mart layers, run by dbt build. The Killercoda scenario adds a per-step verify script, so a reader who mistypes a model doesn't discover it three steps later.

Constraints and non-goals

  • Teaches dbt Core, not dbt Cloud — no orchestration, environments, or job scheduling.
  • The MCP server is deliberately minimal: three tools, no semantic layer, no query planning.
  • Not incremental. The dataset is small enough that everything is a full refresh, so incremental models are named but not taught here.

What I'd do differently

  • Add a part seven on incremental models. It's the first thing that bites in a real project and the tutorial stops just short of it.
  • Give the MCP server the column documentation from the YAML. It currently describes tables structurally, when the descriptions that would make its SQL better are already written.
