jobscout

A crawler that reads companies' own applicant tracking systems rather than aggregators, then filters hard on the three things that actually disqualify a role: seniority, geography, and stated years of experience. Python 3.11, standard library only, no dependencies at all.

Python · HTTP/JSON APIs · Greenhouse · Ashby · Lever · Workday · SmartRecruiters · Recruitee · Workable

Private repository. This one operates against live third-party endpoints and carries a working target list, so the code isn't public. The architecture and results below are the whole of it — happy to walk through the code directly.

The problem

Aggregator search collapses under a specific query. Ask for remote data roles under a given experience ceiling and you get thousands of results dominated by senior and on-site posts, duplicate listings of the same job, and reposts of roles that closed months ago. The filters the aggregators expose — title, location, a "remote" toggle — aren't the filters that decide whether it's worth applying. The years-of-experience requirement, which is the one that actually disqualifies, appears only in the posting body.

The insight

Almost every company job board is a thin front end over one of about seven applicant tracking systems, and each of those exposes the public JSON endpoint that the careers page itself consumes. Read those directly and you get live postings, no duplicates, no expired reposts, and the full description text — which is the only place the real requirement is written down.

Results from a single run

438 live boards discovered · 27,140 postings read · 87 qualifying remote data roles · 15 entry-level software roles

Three decisions worth explaining

Two-phase filtering: cheap discovery, then body verification

Fetching every full description across 27,000 postings is slow and mostly wasted, since title and location eliminate the large majority. Phase one filters on the fields the list endpoints return for free; phase two fetches full bodies only for survivors and checks the stated experience requirement. The ordering is the difference between a run that finishes and one that doesn't.

Zero dependencies, on purpose

requests would have been more comfortable, and a scraping framework would have handled retries and sessions. Neither earns its place: this makes plain GETs against seven JSON APIs, and urllib does that. The payoff is that it runs anywhere Python 3.11 does with no install step and no dependency that can break it six months from now. It's a deliberate constraint, not a missing feature.

Role families in one file, and the "adjacent analyst" bet

Matching rules live in a single ROLE_FAMILIES structure, so re-aiming the whole search is a one-file edit rather than a code change across adapters. The substantive call inside it was adding an adjacent analyst family — product, revenue, operations, marketing analyst — on the theory that these want the same skills under a different department's title. That family is where most of the additional volume came from.

What broke

Unstated experience requirements. The first version dropped any posting where it couldn't parse a years figure, which silently discarded a large share of perfectly good roles — plenty of postings simply don't state a number. The filter was quietly doing the opposite of its job, and because the output still looked reasonable it took a manual spot-check against a company's careers page to notice. The rule is now explicit and documented: unstated always passes. Ambiguity should widen the funnel, not narrow it.

Verification

Every run writes both sides of the decision — qualified.json and rejected.json — so a filter change can be diffed against the previous run rather than trusted. Rejections are the more useful artifact: spot-checking what got dropped is how the unstated-years bug surfaced, and it's the only way to catch a filter that's too aggressive, since an over-filtered result set looks identical to a genuinely thin market.

Constraints and non-goals

  • iCIMS and Taleo are unsupported, which means a meaningful slice of large non-tech employers is invisible.
  • Workday coverage is per-tenant and currently shallow — each tenant has to be added by hand.
  • Company lists are curated, not discovered. It searches a known universe rather than the whole market.
  • No notifications, no scheduling, no database. It's a run-and-read tool that emits Markdown.

What I'd do differently

  • Persist runs to SQLite instead of JSON files, so "what's new since last week" is a query rather than a diff.
  • Add an iCIMS adapter before extending Workday further — it's the bigger coverage gap.
