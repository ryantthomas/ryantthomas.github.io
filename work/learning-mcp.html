learning-mcp

An MCP server that turns Claude into a tutor which cannot skip ahead. It researches a topic, decomposes it into a prerequisite graph, and refuses to release the next element until you've demonstrated mastery of the ones it depends on — on a spaced-repetition schedule.

Python · SQLite · MCP · SM-2 · Docker · GitHub Actions · MIT

The problem

Ask a model to teach you something over several sessions and it collapses the plan. It will lay out a sensible eight-step curriculum, then — because you sounded confident, or because the conversation drifted — deliver step six in the middle of step two, and agree with you that you've understood. Everything that makes teaching work (ordering, checking, spacing) lives in the prompt, and the prompt is a suggestion.

The premise here is that sequencing shouldn't be a request. If the next step is physically unavailable until a prerequisite is marked mastered in a database, the model can't skip it however the conversation goes.

Architecture

Seven tables carry it: topics and concepts hold the researched material, elements and element_edges are the DAG, mastery tracks per-element state, drills holds the questions, and sessions records each sitting. Seven MCP tools expose it. The scheduler implements SM-2, so an element you keep getting right recedes and one you fumble comes back tomorrow.

Scope

Interface7 MCP tools — start a topic, research, decompose, next step, drill, grade, review
Schema7 tables: topics, concepts, elements, element_edges, mastery, drills, sessions
SchedulingSM-2 spaced repetition — per-element ease factor, repetition count, next-due date
Tests5 modules covering the scheduler, the mastery gate, decomposition, the server surface, and the CLI
DeployDockerfile for local or hosted; CI and release workflows

Three decisions worth explaining

The gate is enforced server-side, not prompted

The cheap version is a system prompt saying "do not advance until the learner demonstrates understanding." It works most of the time, which is the problem — the failure is invisible and arrives exactly when you're tired and want to move on. Here the next-step tool returns nothing for a locked element. The model can be as agreeable as it likes; it has no unlocked content to hand over.

A prerequisite DAG instead of an ordered list

A linear syllabus is simpler and encodes a false claim — that there's one valid order. A DAG says what actually depends on what, which means several elements can be legitimately available at once and the learner picks. It also makes the failure mode explicit: a cycle in the graph is a decomposition bug the model made, and it's detectable, where a bad linear ordering just silently teaches things in a confusing sequence.

SM-2 rather than a fixed review interval

Reviewing everything on a fixed schedule spends the same effort on the thing you've known cold for a month as on the thing you got wrong yesterday. SM-2 is decades old, well understood, and needs three columns. I took a known algorithm over inventing a scheduler because the interesting problem here is the gate, not the spacing curve.

What broke

The first decomposition pass produced graphs with cycles — the model would make A a prerequisite of B and B a prerequisite of A, usually for two genuinely intertwined concepts. Nothing crashed. The elements involved simply never unlocked, and the session looked like it had run out of material. It presented as an empty curriculum rather than a graph error, which is why it took a while to find. Cycle detection now runs at decomposition time and rejects the graph before it's stored, where the error is attributable.

Verification

test_scheduler.py pins the SM-2 interval math against known sequences, and test_mastery.py covers the gate itself — that a locked element stays locked, that satisfying the last inbound edge unlocks it, and that a failed drill moves state backwards. Those are the two places where a bug produces a plausible-looking session that teaches the wrong thing in the wrong order.

Constraints and non-goals

  • Single-learner, local SQLite. No classroom or multi-user model.
  • Content quality is the model's, not mine — this governs sequencing and pacing, it doesn't verify that the material is correct.
  • Grading is model-assisted, so it's better at "did you address the concept" than at precise factual scoring.

What I'd do differently

  • Separate researched content from graph structure earlier, so a topic can be re-decomposed without losing the drills already written against it.
  • Store a confidence signal alongside mastery. Right now a lucky guess and a solid answer look identical to the scheduler.
